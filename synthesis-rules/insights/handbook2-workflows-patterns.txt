1.1 IMPLEMENTING RETRIEVAL AUGMENTED GENERATION (RAG)
-----------------------------------------------------------------------------

CAPABILITY OVERVIEW
-------------------
RAG enhances responses by retrieving relevant context from documents before
generation. Performance: 71% baseline → 85% with optimizations.

CORE RAG WORKFLOW
-----------------

PHASE 1: Document Discovery
  Tools Used: Glob, Grep
  Purpose: Find relevant documents in codebase

  Step 1a: Broad Discovery with Glob
    Tool: Glob
    Pattern: "**/*.md" (find all markdown)
    Pattern: "**/*.ipynb" (find all notebooks)
    Pattern: "docs/**/*" (find documentation)

    Parallel execution: Multiple Glob calls in one message
    Example from KGF:
      Glob("**/*.ipynb") → Found 47 notebooks
      Glob("capabilities/**/*.md") → Found capability guides
      Glob("agents/**/*.md") → Found agent patterns

  Step 1b: Content-Based Discovery with Grep
    Tool: Grep
    Pattern: "classification accuracy|performance metrics"
    Output: files_with_matches (get file list first)
    Filter: type="py" or glob="*.md"

    Example from KGF:
      Grep(pattern="capability", type="md") → Found 5 capability docs
      Grep(pattern="agent pattern", output_mode="files_with_matches")
      → Identified relevant source files

PHASE 2: Document Reading & Context Assembly
  Tools Used: Read (parallel), Bash (optional processing)
  Purpose: Load relevant content efficiently

  Step 2a: Parallel Document Reading
    Tool: Read (multiple parallel calls)
    Strategy: Speculative parallel reads

    Best Practice: Read all potentially relevant files in single message
    Example workflow:
      Message contains:
        Read(file_path="doc1.md")
        Read(file_path="doc2.md")
        Read(file_path="doc3.md")
        Read(file_path="doc4.md")
        Read(file_path="doc5.md")

      Result: 5x faster than sequential reads

    Real KGF example:
      Read 5 capability guides in parallel (1 message)
      vs sequential (5 messages) = 5x speedup

  Step 2b: Context Processing (Optional)
    Tool: Bash with jq/grep/awk
    Purpose: Extract specific sections, filter content

    Example: Extract only "best_practices" sections
      Bash: jq '.best_practices' data.json
      Bash: grep -A 5 "## Best Practices" file.md

    Use when: Documents are large and only sections are needed

PHASE 3: Context Assembly & Generation
  Tools Used: (Internal processing)
  Purpose: Assemble context and generate response

  Process:
    1. Organize retrieved documents by relevance
    2. Summarize if context exceeds limits
    3. Structure context with clear sections
    4. Generate response with assembled context

  Context structure:
    """
    CONTEXT FROM DOCUMENTS:

    Document 1: [filename]
    - Key point 1
    - Key point 2

    Document 2: [filename]
    - Key point 1
    - Key point 2

    QUERY: [user question]

    RESPONSE: [generated with context]
    """

PHASE 4: Result Storage (Optional)
  Tools Used: Write
  Purpose: Save results for future reference

  When to use:
    - Results will be referenced repeatedly
    - Building knowledge base
    - Creating documentation

  Example:
    Write(
      file_path="rag-results/analysis-2025-10-30.md",
      content=assembled_response
    )

ADVANCED RAG PATTERNS
----------------------

Pattern 1: Summary Indexing RAG (78% accuracy)
  Workflow:
    1. Glob → find all documents
    2. Read each document in parallel
    3. Generate summary for each (internal)
    4. Write summaries to index file
    5. On query: Read index first
    6. Grep index for relevant doc IDs
    7. Read only relevant full documents
    8. Generate with focused context

  Performance: 71% → 78% accuracy improvement
  Use when: Large document sets (>50 documents)

Pattern 2: Reranking RAG (85% accuracy)
  Workflow:
    1. Initial retrieval (Glob + Grep)
    2. Read top 20 candidates
    3. Score each for relevance (internal)
    4. Rerank by relevance scores
    5. Use top 5 for generation
    6. Generate with highly relevant context

  Performance: 78% → 85% accuracy improvement
  Use when: High precision required

Pattern 3: Contextual Embeddings RAG (95% Pass@10)
  Requires: External embedding system
  Workflow:
    1. Read documents with surrounding context
    2. Generate embeddings with context prefix
    3. Store in vector database (external)
    4. Query retrieves with context awareness
    5. Read retrieved documents
    6. Generate with contextually relevant docs

  Performance: 87% → 95% Pass@10, 35% failure reduction
  Use when: Maximum accuracy required, embeddings available

TOOL COMBINATION MATRIX
------------------------
RAG Phase           Primary Tool    Secondary Tools    Optimization
---------------------------------------------------------------------------
Discovery           Glob            Grep              Parallel Glob calls
Content Search      Grep            -                 Use type parameter
Document Reading    Read            -                 Parallel reads (5x)
Processing          Bash            jq/grep           Only if needed
Assembly            (internal)      -                 Structured formatting
Storage             Write           -                 Optional, for reuse
Indexing            Write + Read    Bash (combine)    For large doc sets

ANTI-PATTERNS
-------------
❌ Sequential reads when parallel possible
   Why: 5x slower, wastes time
   Fix: Multiple Read calls in single message

❌ Reading entire large files without filtering
   Why: Token waste, context overflow
   Fix: Grep first to locate relevant sections, Read with offset/limit

❌ Not caching frequent retrievals
   Why: Repeated work, slower responses
   Fix: Write results to file, Read from cache on subsequent queries

❌ Over-retrieving documents
   Why: Context pollution, reduced accuracy
   Fix: Use Grep to filter, limit to top N most relevant

❌ Under-retrieving documents
   Why: Missing crucial context, incorrect responses
   Fix: Start broad (Glob), then filter (Grep), read generously

  Write results:                    <1 second

Speedup from parallelization:      5x (parallel vs sequential reads)

CAPABILITY OVERVIEW

Document/text classification using Claude. Performance: 70% baseline → 97%

BASIC CLASSIFICATION WORKFLOW
------------------------------

PHASE 1: Prepare Examples (Few-Shot Learning)
  Tools Used: Read, Write
  Purpose: Load example classifications for prompting

  Step 1a: Read Example Data
    Tool: Read
    Files: examples.json, training_data.csv, labeled_samples.txt

    Parallel read strategy:
      Read("examples/category_a_examples.txt")
      Read("examples/category_b_examples.txt")
      Read("examples/category_c_examples.txt")

    Result: Example classifications loaded

  Step 1b: Format Examples
    Tool: (Internal processing)
    Purpose: Structure examples for prompting

    Format:
      """
      Example 1:
      Input: [text]
      Category: A
      Reasoning: [brief explanation]

      Example 2:
      Input: [text]
      Category: B
      Reasoning: [explanation]
      """

  Step 1c: Cache Examples (Optional)
    Tool: Write
    Purpose: Reuse formatted examples

    Write("classification-examples-formatted.txt", formatted_examples)
    Benefit: Prompt caching can reduce cost 90%

PHASE 2: Load Documents to Classify
  Tools Used: Glob, Read
  Purpose: Find and load documents needing classification

  Step 2a: Discover Documents
    Tool: Glob
    Pattern: "data/unclassified/**/*.txt"
    Result: List of documents to classify

  Step 2b: Read Documents
    Tool: Read (parallel if manageable)
    Strategy: Batch reading

    Small dataset (<10 docs): Parallel read all
    Large dataset (>10 docs): Batch read in groups

    Example:
      Batch 1: Read docs 1-10 (parallel)
      Classify batch 1
      Batch 2: Read docs 11-20 (parallel)
      Classify batch 2

PHASE 3: Classify Documents
  Tools Used: (Internal classification)
  Purpose: Assign categories using examples

  Process for each document:
    1. Load example classifications
    2. Present document with examples
    3. Apply classification logic
    4. Determine category with confidence
    5. Generate reasoning

PHASE 4: Store Results
  Tools Used: Write
  Purpose: Save classifications for review

  Format options:
    JSON: Write("results.json", json_output)
    CSV: Write("results.csv", csv_output)
    Markdown: Write("results.md", formatted_output)

  Include:
    - Document ID/name
    - Assigned category
    - Confidence score
    - Reasoning
    - Timestamp

PHASE 5: Validation (Optional)
  Tools Used: Bash
  Purpose: Run evaluation script

  Example:
    Bash: python3 evaluate_classifications.py results.json ground_truth.json

  Output: Accuracy, precision, recall, F1 score

ADVANCED CLASSIFICATION PATTERNS
---------------------------------

Pattern 1: RAG-Enhanced Classification (94% accuracy)
  Combines: RAG workflow + Classification

  Workflow:
    1. Grep for similar classified documents
    2. Read top N similar documents
    3. Use as additional examples
    4. Classify with enriched context

  Example:
    Classifying: "Bug report about login timeout"

    Grep(pattern="login.*timeout", glob="classified/**/*.txt")
    → Finds 3 similar documents

    Read those 3 documents (parallel)
    → Load their classifications

    Classify new document with:
      - Original examples
      - Similar document examples
      - Domain context

  Result: 70% → 94% accuracy improvement

Pattern 2: Chain-of-Thought Classification (82% accuracy)
  Enhances: Basic classification with reasoning steps

  Workflow:
    1. Read examples with detailed reasoning
    2. For each document, think step-by-step:
       a. Identify key features
       b. Compare to category criteria
       c. Evaluate confidence for each category
       d. Select best match with justification
    3. Output classification with reasoning chain

  Prompt structure:
    """
    Document: [text]

    Step 1 - Key Features:
    - [feature 1]
    - [feature 2]

    Step 2 - Category Evaluation:
    Category A: [evaluation] (confidence: X%)
    Category B: [evaluation] (confidence: Y%)

    Step 3 - Decision:
    Selected: Category B
    Reasoning: [detailed justification]
    """

  Result: 70% → 82% accuracy improvement

Pattern 3: RAG + CoT Classification (97% accuracy)
  Combines: RAG + Chain-of-Thought
  Best performance, highest accuracy

  Workflow:
    1. Grep similar documents (RAG)
    2. Read similar documents + examples
    3. Classify with CoT reasoning
    4. Validate against similar cases
    5. Adjust confidence based on similarity

  Result: 70% → 97% accuracy (best possible)

1.3 IMPLEMENTING SUMMARIZATION WITH CLAUDE CODE
-----------------------------------------------------------------------------

CAPABILITY OVERVIEW
-------------------
Document summarization with various approaches: extractive, abstractive,
guided summaries. Critical for legal docs, research papers, long articles.

BASIC SUMMARIZATION WORKFLOW
-----------------------------

PHASE 1: Load Source Document(s)
  Tools Used: Read, Glob (for multiple docs)
  Purpose: Load content to summarize

  Single document:
    Read("document.txt")
    Read("paper.pdf")  # PDF support
    Read("notebook.ipynb")  # Jupyter support

  Multiple documents:
    Glob("reports/*.pdf")
    → Get all report paths

    Read multiple in parallel:
      Read("reports/q1.pdf")
      Read("reports/q2.pdf")
      Read("reports/q3.pdf")
      Read("reports/q4.pdf")

PHASE 2: Determine Summarization Approach
  Tool: (Internal analysis)
  Purpose: Choose best summarization strategy

  Factors:
    - Document length: Short (<1000 words) vs Long (>10000 words)
    - Document type: Legal, technical, narrative, data
    - Output requirements: Length, format, focus areas
    - Use case: Overview, extraction, analysis

  Approaches:
    1. Direct Summarization: Whole doc → summary
    2. Chunked Summarization: Break into sections → summarize each → combine
    3. Extractive Summary: Pull key sentences directly
    4. Abstractive Summary: Rewrite in new words
    5. Guided Summary: Follow specific template/structure

PHASE 3: Generate Summary
  Tool: (Internal summarization)
  Purpose: Create summary using chosen approach

  Direct approach:
    - Single pass over document
    - Generate summary directly
    - Best for: Short documents (<5000 words)

  Chunked approach:
    - Split document into sections
    - Summarize each section
    - Combine section summaries
    - Generate final summary
    - Best for: Long documents (>10000 words)

PHASE 4: Store Summary
  Tool: Write
  Purpose: Save summary for use

  Formats:
    Markdown: Write("summary.md", markdown_summary)
    JSON: Write("summary.json", structured_summary)
    Plain text: Write("summary.txt", text_summary)

  Include:
    - Source document reference
    - Summary date
    - Summarization approach used
    - Key points/findings
    - Word count (original vs summary)

PHASE 5: Validation (Optional)
  Tools: Read, Bash
  Purpose: Validate summary quality

  Manual validation:
    Read original document + Read summary side-by-side
    Check: Coverage, accuracy, coherence

  Automated validation:
    Bash: python3 evaluate_summary.py document.txt summary.txt
    Metrics: ROUGE scores, coverage metrics

BATCH SUMMARIZATION WORKFLOW
-----------------------------
For summarizing many documents efficiently

Step 1: Document Discovery
  Glob("documents/**/*.pdf")
  → Get all document paths

  Count: Bash: find documents/ -name "*.pdf" | wc -l
  → Know total count for planning

Step 2: Batch Strategy
  Small batch (<10 docs): Parallel read + summarize directly
  Medium batch (10-50 docs): Sequential batches, parallel within batch
  Large batch (>50 docs): Write Python script, use Bash to run

Step 3: Create Batch Script (Large Scale)
  Write("batch_summarize.py")
  Content:
    """
    import anthropic
    import os
    import json

    client = anthropic.Anthropic()

    for doc_path in document_paths:
        with open(doc_path) as f:
            content = f.read()

        summary = client.messages.create(
            model="claude-sonnet-4",
            messages=[{
                "role": "user",
                "content": f"Summarize this document:\n\n{content}"
            }]
        )

        # Save summary
        output_path = doc_path.replace('.txt', '-summary.txt')
        with open(output_path, 'w') as f:
            f.write(summary.content[0].text)
    """

Step 4: Execute Batch
  Bash: python3 batch_summarize.py

  Or background:
    Bash(command="python3 batch_summarize.py", run_in_background=True)
    → Continue working while processing

    BashOutput(bash_id="...")
    → Monitor progress

Step 5: Collect Results
  Glob("documents/**/*-summary.txt")
  → Find all generated summaries

  Optional: Combine into master summary
    Read all summaries (parallel if manageable)
    Generate meta-summary
    Write("master-summary.md")

      - LEFT JOIN orders to customers
      - Filter where MAX(order_date) < date('now', '-6 months')
      - OR order_id IS NULL (no orders)

    SQL:
    SELECT c.customer_id, c.name
    FROM customers c
    LEFT JOIN orders o ON c.customer_id = o.customer_id
    GROUP BY c.customer_id, c.name
    HAVING MAX(o.order_date) < date('now', '-6 months')
       OR MAX(o.order_date) IS NULL;

    Content:
      """
      import json

      def chunk_document(text, chunk_size=512, overlap=50):
          chunks = []
          words = text.split()

          for i in range(0, len(words), chunk_size - overlap):
              chunk = ' '.join(words[i:i + chunk_size])
              chunks.append({
                  'chunk_id': f'chunk_{i}',
                  'text': chunk,
                  'start_pos': i
              })

          return chunks

      # Load documents
      with open('documents.json') as f:
          documents = json.load(f)

      # Chunk each document
      all_chunks = []
      for doc in documents:
          chunks = chunk_document(doc['content'])
          for chunk in chunks:
              chunk['doc_id'] = doc['id']
              chunk['doc_title'] = doc['title']
              all_chunks.append(chunk)

      # Save chunks
      with open('chunks.json', 'w') as f:
          json.dump(all_chunks, f, indent=2)
      """

  Execute chunking:
    Bash: python3 chunk_documents.py
    → Creates chunks.json with all chunks

          chunks = json.load(f)

      # Prepare vectors
      vectors = []
      for chunk in chunks:

              'metadata': {

                  'text': chunk['text'],
                  'contextual_text': chunk['contextual_text']
              }
          })

PATTERN OVERVIEW

------------------------------

PROMPT CHAINING PATTERNS
-------------------------

Pattern 1: Linear Chain (Simplest)
  Structure: A → B → C → D → Final

  Each stage has single input, single output
  No branching, no parallelism

  Example: Document → Summary → Translation → Storage

  Implementation:
    result_1 = stage_1()
    result_2 = stage_2(result_1)
    result_3 = stage_3(result_2)
    final = stage_4(result_3)

Pattern 2: Fan-Out Chain
  Structure:
         B
        /
    A<
        \
         C

    Then: B + C → D → Final

  One stage produces multiple outputs for parallel processing
  Results combined in later stage

  Example: Extract → (Capabilities + Patterns + Skills) → Combine

  Implementation (in Claude Code):
    base = stage_1()  # Schema definition

    # Parallel execution
    cap = stage_2a(base)   # Extract capabilities
    pat = stage_2b(base)   # Extract patterns
    ski = stage_2c(base)   # Extract skills

    # Combine
    combined = stage_3(cap, pat, ski)

Pattern 3: Conditional Chain
  Structure:
         B → D
        /
    A<
        \
         C → E

  Chain path depends on intermediate results

  Example: Analyze → (Simple path OR Complex path) → Result

  Implementation:
    analysis = stage_1()

    if analysis['complexity'] == 'simple':
        result = simple_path(analysis)
    else:
        result = complex_path(analysis)

    final = finalize(result)

Pattern 4: Iterative Chain (with validation)
  Structure: A → B → C → Validate → (if fail: B → C → Validate) → Final

  Stages repeat until validation passes

  Example: Generate → Test → (if fail: Refine → Test) → Store

  Implementation:
    draft = generate()

    while True:
        validation = test(draft)
        if validation['passed']:
            break
        draft = refine(draft, validation['feedback'])

    store(draft)

TOOL USAGE IN PROMPT CHAINING
------------------------------

Chains primarily use:
  1. **Read** - Load inputs for each stage
  2. **Write** - Store intermediate outputs
  3. **Bash** - Execute stage scripts, combine data
  4. **(Internal)** - Processing within stages

Tool combination example (KGF extraction):
  Stage: Glob → Read → (Process) → Write → Read → Bash (combine)

  Glob finds files
  Read loads files
  Process extracts data
  Write stores stage output
  Read loads for next stage
  Bash combines multiple outputs

ANTI-PATTERNS
-------------
❌ Not storing intermediate outputs
   Why: If chain fails, lose all progress
   Fix: Write stage outputs to files

❌ Making chains too long (>10 stages)
   Why: Hard to debug, fragile
   Fix: Break into smaller chains or use Orchestrator-Workers

❌ Not validating between stages
   Why: Errors propagate and compound
   Fix: Add validation checks between stages

❌ Parallel stages that aren't actually independent
   Why: Race conditions, dependency errors
   Fix: Ensure true independence or sequence them

PERFORMANCE METRICS
-------------------
Prompt Chaining characteristics:
  Complexity: Low
  Latency: Sum of all stage latencies
  Reliability: Product of stage reliabilities

KGF extraction chain (10 stages):
  Total time: ~4 hours
  Longest stage: Stage 3-6 (extractions, ~1 hour each)
  Shortest stage: Stage 2 (schema, ~30 min)
  Success rate: 100% (no stage failures)

Compared to monolithic approach:
  Monolithic: Would need full context, likely exceed limits
  Chaining: Each stage uses fresh context, no limit issues

2.4 IMPLEMENTING ORCHESTRATOR-WORKERS PATTERN
-----------------------------------------------------------------------------

PATTERN OVERVIEW
----------------
Dynamic task breakdown with delegation to specialized workers.
Complexity: High
Best for: Complex multi-step tasks, parallel sub-task execution

CORE ORCHESTRATOR-WORKERS WORKFLOW
-----------------------------------

PHASE 1: Task Analysis (Orchestrator)
  Tool: (Planning)
  Purpose: Break down complex task into manageable sub-tasks

  Process:
    1. Analyze overall task requirements
    2. Identify independent sub-tasks
    3. Determine task dependencies
    4. Allocate sub-tasks to workers
    5. Define success criteria

PHASE 2: Worker Delegation
  Tool: Task (agent launcher)
  Purpose: Delegate sub-tasks to specialized workers

  Implementation:
    # Launch multiple workers in parallel
    Single message with multiple Task calls:
      Task(subagent_type="general-purpose", 
           prompt="Worker 1: Extract capability nodes...",
           description="Extract capabilities")

      Task(subagent_type="general-purpose",
           prompt="Worker 2: Extract agent patterns...",
           description="Extract patterns")

      Task(subagent_type="general-purpose",
           prompt="Worker 3: Extract skills...",
           description="Extract skills")

PHASE 3: Worker Execution
  Tool: Task agents execute autonomously
  Purpose: Complete assigned sub-tasks independently

  Each worker:
    - Has access to all tools
    - Works independently
    - Returns complete result
    - Cannot communicate with other workers

PHASE 4: Result Collection (Orchestrator)
  Tool: (Internal processing)
  Purpose: Collect and validate worker results

  Process:
    1. Wait for all workers to complete
    2. Collect results from each worker
    3. Validate completeness and quality
    4. Identify any failures

PHASE 5: Result Integration (Orchestrator)
  Tools: Write, Bash (combining)
  Purpose: Combine worker results into final output

  Process:
    1. Merge worker outputs
    2. Resolve any conflicts
    3. Fill gaps if needed
    4. Generate final integrated result

ORCHESTRATOR-WORKERS PATTERNS
------------------------------

Pattern 1: Parallel Independent Workers
  Use when: Sub-tasks have no dependencies

  Structure:
    Orchestrator → Worker 1 (task A)
                → Worker 2 (task B)
                → Worker 3 (task C)
                → Collect results → Integrate

  Maximum parallelization

Pattern 2: Sequential Stages with Workers
  Use when: Some dependencies exist

  Structure:
    Orchestrator → Stage 1: Workers for tasks A, B, C (parallel)
                → Stage 2: Workers for tasks D, E (parallel, depend on Stage 1)
                → Integrate

  Workers within stage run in parallel
  Stages run sequentially

Pattern 3: Map-Reduce with Workers
  Use when: Same operation on multiple inputs

  Structure:
    Orchestrator → Map: Launch worker for each input (parallel)
                → Collect all results
                → Reduce: Combine results

  Example: Process 100 documents
    - Launch 10 workers, each processing 10 documents
    - Collect 10 results
    - Combine into final output

Pattern 4: Recursive Orchestration
  Use when: Sub-tasks themselves need orchestration

  Structure:
    Orchestrator → Worker 1 (acts as sub-orchestrator)
                           → Sub-worker 1a
                           → Sub-worker 1b
                → Worker 2 (simple worker)
                → Integrate

  Workers can themselves orchestrate sub-workers
  Creates hierarchical task decomposition

TOOL COMBINATION FOR ORCHESTRATOR-WORKERS
------------------------------------------

Orchestrator uses:
  1. **Task** - Launch workers (parallel launch)
  2. **Write** - Store integration results
  3. **Bash** - Combine worker outputs
  4. **Read** - Validate worker results

Workers use:
  - Any tools needed for their sub-task
  - Typically: Glob, Read, Write, Bash

Example orchestration:
  # Orchestrator
  Task(...worker 1...)
  Task(...worker 2...)
  Task(...worker 3...)
  
  # Wait for completion
  
  # Integration
  Bash: combine outputs
  Write: integrated result

ADVANCED ORCHESTRATION: ADAPTIVE TASK ALLOCATION
-------------------------------------------------

Pattern: Orchestrator adjusts based on worker results

Phase 1: Initial delegation
  Launch workers for initial sub-tasks

Phase 2: Mid-flight adjustment
  If worker reports unexpected complexity:
    - Launch additional workers
    - Re-allocate tasks
    - Adjust plan

Phase 3: Failure handling
  If worker fails:
    - Analyze failure reason
    - Retry with different approach
    - Or delegate to specialized worker

Example:
  Initial plan: 3 workers to process 300 documents

  Worker 1 reports: "Documents are more complex than expected"
  
  Orchestrator adjusts:
    - Launch 3 additional workers
    - Redistribute 300 documents across 6 workers
    - Each worker now processes 50 documents

ANTI-PATTERNS
-------------
❌ Using Orchestrator-Workers for simple tasks
   Why: Overhead not worth it, slower than direct approach
   Fix: Use Orchestrator-Workers only for truly complex tasks

❌ Workers with dependencies on other workers
   Why: Defeats parallelization, creates race conditions
   Fix: Ensure workers are truly independent

❌ Not handling worker failures
   Why: One failure breaks entire workflow
   Fix: Validate worker results, retry on failure

❌ Too many workers (>10)
   Why: Coordination overhead, diminishing returns
   Fix: Limit to 5-10 workers, or use batch processing

❌ Workers that are too granular
   Why: Coordination overhead exceeds work time
   Fix: Each worker should do substantial work (>5 min)

  Complexity: High
  Latency: Max(worker latencies) + orchestration overhead
  Speedup: Near-linear for independent workers

  - 3-10 independent sub-tasks
  - Each sub-task takes >5 minutes
  - Sub-tasks are truly independent

  Launch workers: ~1-2 minutes

  Total: ~5-10 minutes overhead

2.5 IMPLEMENTING EVALUATOR-OPTIMIZER PATTERN
-----------------------------------------------------------------------------

PATTERN OVERVIEW
----------------
Iterative refinement loops where evaluator assesses output and optimizer
improves based on feedback.
Complexity: High
Best for: Quality-critical tasks, iterative improvement

CORE EVALUATOR-OPTIMIZER WORKFLOW
----------------------------------

PHASE 1: Initial Generation (Optimizer)
  Tools: Various (depends on task)
  Purpose: Create initial output

  Process:
    1. Understand requirements
    2. Generate first version
    3. Store for evaluation

PHASE 2: Evaluation (Evaluator)
  Tools: Read, Bash (test scripts)
  Purpose: Assess quality of output

  Process:
    1. Load generated output
    2. Apply evaluation criteria
    3. Identify specific issues
    4. Generate actionable feedback

  Evaluation methods:
    - Code: Run tests, check syntax, analyze quality
    - Text: Check grammar, completeness, accuracy
    - Data: Validate format, check completeness, verify correctness

PHASE 3: Decision Point
  Tool: (Internal analysis)
  Purpose: Determine if refinement needed

  Criteria:
    if quality >= threshold:
        Accept and finalize
    elif iterations < max_iterations:
        Optimize and re-evaluate
    else:
        Accept best version or escalate

PHASE 4: Optimization (Optimizer)
  Tools: Edit, Write
  Purpose: Improve output based on feedback

  Process:
    1. Analyze evaluation feedback
    2. Identify specific changes needed
    3. Apply improvements
    4. Store improved version

PHASE 5: Iteration Loop
  Tools: (Loop control)
  Purpose: Repeat evaluation-optimization until satisfied

  Loop:
    While quality < threshold AND iterations < max:
      Evaluate current version
      Generate feedback
      Optimize based on feedback
      Increment iteration counter

ANTI-PATTERNS

   Why: Can't rollback if optimization makes things worse
   Fix: Write each version (v1, v2, v3, etc.)

   Why: Inconsistent assessment, unclear goals

❌ Over-optimizing (too many iterations)

3.1 IMPLEMENTING PROMPT CACHING FOR COST OPTIMIZATION
-----------------------------------------------------------------------------

TECHNIQUE OVERVIEW
------------------
Cache frequently used prompts to reduce costs by 90% and improve latency 2x.
Best for: Repeated operations with shared context.

IMPLEMENTATION WORKFLOW
-----------------------

Phase 1: Identify Cacheable Content
  Analyze workflow for repeated content:
    - Schema documents (reused across queries)
    - Example sets (reused for few-shot learning)
    - System instructions (reused for all requests)
    - Large reference documents

Phase 2: Structure for Caching
  Tools: Write
  Purpose: Organize content to maximize cache hits

  Write cacheable content to files:
    Write("cached-schema.md", schema_content)
    Write("cached-examples.txt", examples)
    Write("cached-instructions.txt", system_prompt)

Phase 3: Use Cached Content
  Tools: Read
  Purpose: Load and reuse cached content

  Read("cached-schema.md") → Loaded once, cached
  Read("cached-examples.txt") → Cached
  
  For multiple operations:
    Operation 1: Read + use (cache miss, pay full)
    Operation 2: Read + use (cache hit, pay 10%)
    Operation 3: Read + use (cache hit, pay 10%)
    ...
    
  Cost savings: 90% reduction after first operation

Real-World Use Case: Classification with Examples
  Without caching:
    Every classification loads examples fresh
    100 classifications = 100× full cost

PART 5: PERFORMANCE OPTIMIZATION PATTERNS
=============================================================================

Comprehensive patterns for optimizing workflows discovered through practice.

-----------------------------------------------------------------------------
5.1 PARALLELIZATION OPTIMIZATION
-----------------------------------------------------------------------------

PRINCIPLE
---------
Maximize concurrent operations to minimize total workflow time.

STRATEGIES
----------

1. Batch Independent Reads
   Before: 5 sequential Read calls = 15 seconds
   After: 5 parallel Reads in one message = 3 seconds
   Speedup: 5x

2. Group Independent Bash Commands
   Before: 3 sequential Bash calls = 6 seconds
   After: 3 parallel Bash calls = 2 seconds
   Speedup: 3x

3. Parallel Discovery
   Single message with:
     Glob("**/*.py")
     Glob("**/*.js")
     Glob("**/*.md")
   Result: All patterns found simultaneously

4. Optimal Batch Sizes
   Best: 5-10 parallel operations
   Too few (<3): Underutilized parallelism
   Too many (>20): Diminishing returns

ANTI-PATTERNS
-------------
- Reading files sequentially when independent
- Not batching Bash commands
- Parallelizing operations with dependencies

TOOLS OPTIMIZED
---------------
Read, Bash, Glob, Grep (all support parallelization)

-----------------------------------------------------------------------------
5.2 CONTEXT MANAGEMENT OPTIMIZATION
-----------------------------------------------------------------------------

PRINCIPLE
---------
Minimize context usage to enable larger workflows and reduce costs.

STRATEGIES
----------

1. Progressive Summarization
   Instead of keeping full context:
     Stage 1: Extract nodes → Summarize "5 nodes extracted"
     Stage 2: Use summary, not full node details
   
   Benefit: Prevents context overflow in long chains

2. External Storage for Intermediate Results
   Write stage outputs to files:
     Write("stage1-output.json")
   
   Next stage reads only what's needed:
     Read specific sections, not entire history

3. Chunked Processing for Large Documents
   Read with offset/limit:
     Read(file, offset=0, limit=2000)
     Process chunk
     Read(file, offset=2000, limit=2000)
     Process chunk
   
   vs Reading entire 10,000-line file at once

4. Selective Reading
   Use Grep to find relevant sections first:
     Grep(pattern="section", path="large-doc.md")
     → Identify lines 500-600
     Read(file, offset=500, limit=100)
   
   vs Reading entire file

ANTI-PATTERNS
-------------
- Reading same large file repeatedly
- Keeping all intermediate results in context
- Not using file storage for stage outputs

TOOLS OPTIMIZED
---------------
Read (offset/limit), Write (stage outputs), Grep (selective location)

-----------------------------------------------------------------------------
5.3 VALIDATION OPTIMIZATION
-----------------------------------------------------------------------------

PRINCIPLE
---------
Catch errors early to avoid expensive rework.

STRATEGIES
----------

1. Incremental Validation
   After each stage:
     Write output
     Bash: validate script
     Confirm success before proceeding
   
   vs Validating only at end (risk losing all work)

2. Syntax Validation Before Execution
   For SQL:
     Bash: sqlite3 db.db "EXPLAIN QUERY PLAN [SQL]"
   
   For Python:
     Bash: python3 -m py_compile script.py
   
   Catch errors before expensive operations

3. Test-Driven Development Pattern
   Write tests first:
     Write("tests/test_function.py")
   
   Implement code:
     Write("src/function.py")
   
   Validate immediately:
     Bash: pytest tests/test_function.py

4. Progressive Quality Gates
   Gate 1: Syntax correct? (fast check)
   Gate 2: Logic correct? (unit tests)
   Gate 3: Performance acceptable? (benchmarks)
   Gate 4: Integration works? (end-to-end tests)
   
   Each gate prevents proceeding with flawed output

ANTI-PATTERNS
-------------
- Waiting until end to validate
- Not testing intermediate outputs
- Proceeding despite validation failures

TOOLS OPTIMIZED
---------------
Bash (validation scripts), Read (check outputs)
