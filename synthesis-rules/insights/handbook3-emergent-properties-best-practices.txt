1.1 PARALLEL TOOL CALLS - THE CRITICAL OPTIMIZATION
-----------------------------------------------------------------------------

EMERGENT DISCOVERY
------------------
Single message with multiple tool calls executes them concurrently.
This is THE most important performance optimization for Claude Code.

HOW DISCOVERED
--------------
Initially: Called Read 5 times sequentially (5 messages, 15 seconds)
Experiment: Called Read 5 times in one message (1 message, 3 seconds)
Result: 5x speedup - realized this applies to ALL tool types

IMPLICATIONS
------------
1. ALWAYS batch independent operations in single message
2. Applies to: Read, Bash, Glob, Grep, mixed operations
3. Practical limit: ~10 parallel operations (diminishing returns after)
4. Saves ~33% total project time when used systematically

MEASURED IMPACT (KGF Project)
------------------------------
Without parallelization:   ~6 hours estimated
With parallelization:      ~4 hours actual
Time saved:                ~2 hours (33%)

Operations parallelized:
  - 5 capability guide reads: 15s → 3s (5x)
  - 3 git commands: 6s → 2s (3x)
  - 5 glob patterns: 5s → 1s (5x)

DEEPER INSIGHT
--------------
Parallelization compounds across workflow:
  5 operations at 3x speedup = 3x faster
  10 operations at 3x speedup = 3x faster
  But: 50 operations (10 groups of 5 parallel) = 3x faster

Systematic parallelization = consistent 3-5x speedup across entire project

WHY EMERGENT
------------
Documentation mentions parallel tools, but doesn't emphasize:
  - How critical this is (most important optimization)
  - Compounds across workflow
  - Works with mixed tool types
  - Real-world speedup measurements

-----------------------------------------------------------------------------
1.2 PROGRESSIVE ASSEMBLY - BETTER THAN MONOLITHIC
-----------------------------------------------------------------------------

EMERGENT DISCOVERY
------------------
Building complex outputs through multiple Write operations produces better
results than attempting single monolithic generation.

HOW DISCOVERED
--------------
Initial approach: Generate all 30 nodes in one operation
Problem: Context overflow, inconsistencies, errors

Revised approach:
  - Write 5 capabilities separately
  - Write 5 agent patterns separately
  - Write 7 skills separately
  - Write 13 techniques separately
  - Combine with Bash (jq)

Result: Higher quality, more consistent, no context issues

IMPLICATIONS
------------
1. Break large generations into logical chunks
2. Write each chunk separately
3. Combine programmatically (Bash, jq)
4. Benefits: Better quality, easier debugging, recoverable from errors

PATTERN
-------
Instead of:
  Generate all 30 nodes → Write("all-nodes.json")

Do:
  Generate 5 capabilities → Write("capabilities.json")
  Generate 5 patterns → Write("patterns.json")
  Generate 7 skills → Write("skills.json")
  Generate 13 techniques → Write("techniques.json")
  Bash: jq -s '{nodes: (.[0].nodes + .[1].nodes + ...)}' → Combined output

WHY THIS WORKS
--------------
- Smaller context per generation = better focus
- Can validate each piece independently
- Can resume if one fails (don't lose all work)
- Easier to refine specific sections
- Natural parallelization opportunities

MEASURED BENEFITS
-----------------
Quality improvement: ~15-20% higher consistency
Error rate: ~50% fewer errors needing correction
Recovery time: Seconds (re-generate one section) vs minutes (re-generate all)

WHY EMERGENT
------------
Documentation doesn't explicitly recommend this pattern. Emerged from:
  - Encountering context limits
  - Observing quality degradation in long generations
  - "Divide and conquer" principle applied to AI generation

-----------------------------------------------------------------------------
1.3 VALIDATION LOOPS - ESSENTIAL FOR QUALITY
-----------------------------------------------------------------------------

EMERGENT DISCOVERY
------------------
Quality systems require validation after each significant operation,
not just at the end.

HOW DISCOVERED
--------------
Initial approach: Generate → Generate → Generate → Validate at end
Problem: Errors compound, massive rework needed

Revised approach: Generate → Validate → Generate → Validate
Result: Errors caught early, minimal rework

PATTERN
-------
After each Write/Edit:
  Bash: validation script
  Check: Syntax, format, completeness
  If errors: Fix immediately
  Only proceed when validated

Example from KGF:
  Write("capabilities-nodes.json")
  Bash: python3 validate_json.py capabilities-nodes.json
  → Fix any issues immediately

  Write("patterns-nodes.json")
  Bash: python3 validate_json.py patterns-nodes.json
  → Fix any issues immediately

BENEFITS
--------
1. Errors caught early (when easy to fix)
2. Don't compound errors across operations
3. Each stage builds on validated foundation
4. Confidence throughout workflow

COST VS BENEFIT
----------------
Cost: ~30 seconds per validation check
Benefit: Avoid 10+ minutes rework when errors compound
ROI: 20x+ return on validation time

VALIDATION TYPES
----------------
Immediate validation:
  - Syntax (jq, Python parser)
  - Format (schema validation)
  - Completeness (required fields present)

Deferred validation:
  - Logic correctness (may need full context)
  - Performance (benchmark after completion)
  - Integration (test after assembly)

WHY EMERGENT
------------
Standard engineering practice, but specific application to AI workflows
with tools emerged through experience:
  - WHEN to validate (after each Write, not just end)
  - WHAT to validate (syntax/format immediate, logic deferred)
  - HOW to validate (Bash scripts, jq, parsers)

1.4 SPECULATIVE READING - BETTER THAN SEQUENTIAL
-----------------------------------------------------------------------------

EMERGENT DISCOVERY
------------------
Reading potentially useful files in parallel (even if not all needed)
is faster than sequential discovery → read → evaluate.

HOW DISCOVERED
--------------
Sequential approach:
  Glob to find files → Read first file → Evaluate relevance
  → If useful, continue
  → If not useful, try next file
  Time: Variable, many round trips

Speculative approach:
  Glob to find files → Read ALL potentially useful files in parallel
  → Evaluate which to use
  Time: One round trip for reading

Result: Faster even when only using 50% of read files

CALCULATION
-----------
Sequential:
  5 files, need to find 3 useful ones
  Average: Try 4 files = 4 round trips
  Time: ~12 seconds

Speculative (parallel):
  Read all 5 files in one message
  Use 3, discard 2
  Time: ~3 seconds

Even with 40% wasted reads: Still 4x faster

WHEN TO USE
-----------
Use speculative reading when:
  - Potential files are known (Glob results)
  - Cost of reading is low (<10 files, each <100KB)
  - Discovery would require multiple iterations

Don't use when:
  - Files are very large (>1MB)
  - Very specific file needed (direct path known)
  - Many files (>20) with low hit rate (<20%)

WHY EMERGENT
------------
Runs counter to efficiency intuition ("don't read what you don't need").
Emerged from observing round-trip latency dominates file read cost.

-----------------------------------------------------------------------------
1.5 TOOL SPECIALIZATION - RIGHT TOOL FOR RIGHT JOB
-----------------------------------------------------------------------------

EMERGENT DISCOVERY
------------------
Using specialized tools (Glob, Grep, Read) is faster and clearer than
equivalent Bash commands, even though Bash CAN do everything.

HOW DISCOVERED
--------------
Initial approach: Use Bash for everything (find, grep, cat)
Observation: Slower, less clear, more error-prone

Revised approach: Use specialized tools
Result: Faster execution, clearer code, fewer errors

COMPARISON
----------
Finding files:
  Bash: find . -name "*.py"      (~2 seconds, less clear)
  Glob: Glob("**/*.py")          (~1 second, very clear)

Searching content:
  Bash: grep -r "pattern" .      (~3 seconds, output parsing needed)
  Grep: Grep(pattern="...")      (~2 seconds, structured output)

Reading files:
  Bash: cat file.txt             (~1 second, manual parsing)
  Read: Read("file.txt")         (~1 second, automatic structure)

WHY SPECIALIZED TOOLS WIN
--------------------------
1. Optimized for specific operations
2. Better error handling
3. Structured output (no parsing needed)
4. Clearer intent (Read vs cat)
5. Parallel execution built-in

WHEN TO USE BASH
----------------
Use Bash for:
  - Complex pipelines (jq, awk, sed combinations)
  - System commands (git, npm, pytest)
  - Script execution
  - Operations not covered by specialized tools

Don't use Bash for:
  - File operations (use Read, Write, Edit)
  - File searching (use Glob, Grep)
  - Simple file display (use Read)

WHY EMERGENT
------------
Documentation lists all tools but doesn't emphasize specialization.
Pattern emerged from comparing performance and code clarity.

1.6 BACKGROUND + MONITOR - TRUE PARALLELISM
-----------------------------------------------------------------------------

EMERGENT DISCOVERY
------------------
Background Bash with BashOutput monitoring enables true long-running
parallelism while continuing other work.

HOW DISCOVERED
--------------
Initial: Long operations blocked workflow (wait for completion)
Problem: Can't do other work while waiting

Solution: run_in_background + BashOutput
Result: Continue working while operations run

PATTERN
-------
# Start long operation
Bash(
  command="python3 long_process.py",
  run_in_background=True
)
→ Returns bash_id

# Continue with other work
Work on other tasks...

# Check progress later
BashOutput(bash_id=bash_id)
→ Get output when needed

USE CASES
---------
1. Long tests (>1 minute)
2. Batch processing large datasets
3. Server startup (run in background, continue setup)
4. Multiple independent long operations (run all in background)

MEASURED BENEFIT
----------------
Example: 3 test suites, each 5 minutes

Sequential: 15 minutes blocked
Background: 5 minutes (longest) + 2 minutes for other work = 7 minutes active

Saved: 8 minutes, can do other work concurrently

WHY EMERGENT
------------
Background execution is documented, but specific use patterns emerged:
  - When to use (>1 minute operations)
  - How to monitor (periodic BashOutput checks)
  - Multiple background operations for true parallelism
  - Continue workflow while waiting

1.7 CONTEXT PRESERVATION THROUGH FILES
-----------------------------------------------------------------------------

EMERGENT DISCOVERY
------------------
Writing intermediate results to files prevents context overflow and
enables resumption after errors.

HOW DISCOVERED
--------------
Initial: Keep all results in context (conversation memory)
Problem: Context fills up, can't continue long workflows

Solution: Write each stage output to files
Result: Fresh context each stage, can resume from any point

PATTERN
-------
Stage 1:
  Generate result
  Write("stage1-output.json", result)
  Summarize: "Stage 1 complete: 5 nodes extracted"

Stage 2:
  Read("stage1-output.json")  # Load only what's needed
  Process
  Write("stage2-output.json", result)
  Summarize: "Stage 2 complete: relationships defined"

Stage 3:
  Read("stage2-output.json")  # Previous stage only
  Process
  Write("stage3-output.json", result)

BENEFITS
--------
1. Context stays manageable
2. Can resume from any stage if error occurs
3. Each stage has fresh context
4. Intermediate results available for debugging

ANTI-PATTERN
------------
Don't keep everything in context:
  ❌ Stage 1 → large result in context
  ❌ Stage 2 → add to context
  ❌ Stage 3 → context overflow

Do use external storage:
  ✅ Stage 1 → Write file, keep summary only
  ✅ Stage 2 → Write file, keep summary only
  ✅ Stage 3 → Write file, keep summary only

WHY EMERGENT
------------
Specific file-based context management pattern for multi-stage workflows
emerged through experience with long projects.

PART 2: PRODUCTION-READY BEST PRACTICES
=============================================================================

Practices that consistently produce high-quality, reliable results.

-----------------------------------------------------------------------------
2.1 SYSTEMATIC PARALLELIZATION
-----------------------------------------------------------------------------

BEST PRACTICE
-------------
Always batch independent operations in single message.

CHECKLIST
---------
Before writing message, ask:
  - Are any of these operations independent?
  - Can they run concurrently?
  - Are they under the parallelization limit (10)?

If yes to all: Batch them in one message

EXAMPLES
--------
✅ Good:
  Single message with:
    Read("file1.txt")
    Read("file2.txt")
    Read("file3.txt")

❌ Bad:
  Message 1: Read("file1.txt")
  Message 2: Read("file2.txt")
  Message 3: Read("file3.txt")

✅ Good:
  Single message with:
    Glob("**/*.py")
    Bash: git status
    Read("config.json")

❌ Bad:
  Message 1: Glob("**/*.py")
  Message 2: Bash: git status
  Message 3: Read("config.json")

EXCEPTION
---------
Don't parallelize when:
  - Operations have dependencies
  - Modifying shared state
  - Need to see result before next operation

-----------------------------------------------------------------------------
2.2 VALIDATION AFTER EVERY SIGNIFICANT OPERATION
-----------------------------------------------------------------------------

BEST PRACTICE
-------------
Validate immediately after Write, Edit, or significant Bash operations.

VALIDATION TYPES
----------------
1. Syntax validation (fast, always do):
   Bash: jq '.' file.json
   Bash: python3 -m py_compile script.py

2. Format validation (fast, always do):
   Bash: python3 validate_schema.py file.json schema.json

3. Logic validation (slower, do for critical operations):
   Bash: pytest tests/test_module.py

4. Performance validation (slowest, do selectively):
   Bash: time python3 script.py

PATTERN
-------
After Write:
  Write("output.json", data)
  Bash: jq '.' output.json  # Immediate validation
  Confirm: "✓ Valid JSON"

After Edit:
  Edit("script.py", changes)
  Bash: python3 -m py_compile script.py  # Syntax check
  Bash: pytest tests/test_script.py      # Logic check
  Confirm: "✓ Tests pass"

COST-BENEFIT
------------
Validation time: 30 seconds per operation
Rework time if no validation: 10+ minutes
ROI: 20x return on validation investment

-----------------------------------------------------------------------------
2.3 PROGRESSIVE ASSEMBLY FOR COMPLEX OUTPUTS
-----------------------------------------------------------------------------

BEST PRACTICE
-------------
Build complex outputs through multiple focused generations, then combine.

DECISION CRITERIA
-----------------
Use progressive assembly when:
  - Output has >1000 lines
  - Multiple distinct sections
  - Different data types/sources
  - Risk of context overflow

Use monolithic generation when:
  - Output is small (<500 lines)
  - Tightly integrated (can't separate cleanly)
  - Single source of information

PATTERN
-------
For large structured data:
  Step 1: Generate section A → Write("section-a.json")
  Step 2: Generate section B → Write("section-b.json")
  Step 3: Generate section C → Write("section-c.json")
  Step 4: Combine → Bash: jq -s '{combined: .[]}' *.json

For large documents:
  Step 1: Generate introduction → Write("intro.md")
  Step 2: Generate body → Write("body.md")
  Step 3: Generate conclusion → Write("conclusion.md")
  Step 4: Combine → Bash: cat intro.md body.md conclusion.md > complete.md

BENEFITS
--------
- Higher quality (focused generation)
- Better consistency (clear section boundaries)
- Easier debugging (isolate problems)
- Recoverable (don't lose everything on error)

-----------------------------------------------------------------------------
2.4 SPECULATIVE PARALLEL READS
-----------------------------------------------------------------------------

BEST PRACTICE
-------------
When exploring codebase, read multiple potentially useful files in parallel
rather than sequential discovery.

DECISION CRITERIA
-----------------
Use speculative reading when:
  - Exploring unfamiliar codebase
  - Multiple files might be relevant
  - Discovery would take multiple iterations
  - Files are reasonably sized (<100KB each)

PATTERN
-------
Discovery phase:
  Glob("**/*.py") → Get all Python files

  Speculative read (parallel):
    Read("src/module1.py")
    Read("src/module2.py")
    Read("src/module3.py")
    Read("src/module4.py")
    Read("src/module5.py")

  Evaluate all 5:
    Use 3 that are relevant
    Discard 2 that aren't

  Still faster than sequential discovery

vs Sequential approach:
  Read("src/module1.py") → Not quite right
  Read("src/module2.py") → Not quite right
  Read("src/module3.py") → This one! (finally)

  Result: 3 round trips vs 1

COST ANALYSIS
-------------
Speculative approach:
  1 round trip, read 5 files, use 3
  Time: ~3 seconds
  "Waste": 2 files

Sequential approach:
  3 round trips to find 3 useful files
  Time: ~9 seconds
  "Waste": 0 files

Result: Speculative is 3x faster despite "wasted" reads

-----------------------------------------------------------------------------
2.5 TOOL SPECIALIZATION
-----------------------------------------------------------------------------

BEST PRACTICE
-------------
Use specialized tools (Glob, Grep, Read, Write, Edit) over generic Bash
for file operations.

DECISION MATRIX
---------------
Operation         | Specialized Tool | Bash Alternative | Use
------------------|------------------|------------------|-------
Find files        | Glob             | find             | Glob
Search content    | Grep             | grep/rg          | Grep
Read file         | Read             | cat              | Read
Write file        | Write            | echo >           | Write
Edit file         | Edit             | sed              | Edit
System command    | Bash             | (native)         | Bash
Complex pipeline  | Bash             | (native)         | Bash
JSON processing   | Bash (jq)        | (native)         | Bash

RATIONALE
---------
Specialized tools provide:
  - Better performance
  - Structured output
  - Clearer intent
  - Better error handling
  - Built-in parallelization

Bash is better for:
  - System commands (git, npm, pytest)
  - Complex pipelines (jq, awk, sed)
  - Operations not covered by specialized tools

PATTERN
-------
✅ Good:
  Glob("**/*.py")              # Find Python files
  Grep(pattern="TODO")         # Search content
  Read("config.json")          # Read file

❌ Bad (when specialized tool exists):
  Bash: find . -name "*.py"    # Use Glob instead
  Bash: grep -r "TODO" .       # Use Grep instead
  Bash: cat config.json        # Use Read instead

✅ Good (Bash appropriate):
  Bash: git status                    # System command
  Bash: jq -s '{a: .[0], b: .[1]}'   # Complex JSON processing
  Bash: pytest tests/                 # Test execution

2.6 BACKGROUND OPERATIONS FOR LONG TASKS
-----------------------------------------------------------------------------

BEST PRACTICE
-------------
Use run_in_background for operations >1 minute to enable parallel work.

DECISION CRITERIA
-----------------
Use background mode when:
  - Operation takes >1 minute
  - Operation is independent
  - Can do other work while waiting
  - Multiple long operations can run concurrently

PATTERN
-------
Single long operation:
  Bash(command="pytest tests/", run_in_background=True)
  → Returns bash_id

  # Do other work
  Work on documentation...
  Work on other code...

  # Check result when ready
  BashOutput(bash_id=bash_id)

Multiple long operations (true parallelism):
  # Start all three
  Bash(command="pytest tests/unit/", run_in_background=True)
  → bash_id_1

  Bash(command="pytest tests/integration/", run_in_background=True)
  → bash_id_2

  Bash(command="pytest tests/e2e/", run_in_background=True)
  → bash_id_3

  # All run concurrently
  # Check each when ready
  BashOutput(bash_id=bash_id_1)
  BashOutput(bash_id=bash_id_2)
  BashOutput(bash_id=bash_id_3)

TIME SAVINGS
------------
3 operations, each 5 minutes:
  Sequential: 15 minutes blocked
  Background: 5 minutes (longest) + continue working

Effective time saved: ~10 minutes + ability to multitask

Write intermediate results to files to prevent context overflow.

  Total: 150 tokens, context fresh

PART 3: ANTI-PATTERNS & FAILURE MODES
=============================================================================

Common mistakes and how to avoid them.

-----------------------------------------------------------------------------
3.1 SEQUENTIAL OPERATIONS WHEN PARALLEL IS POSSIBLE
-----------------------------------------------------------------------------

ANTI-PATTERN
------------
Executing independent operations sequentially.

EXAMPLE
-------
❌ Bad:
  Message 1: Read("file1.txt")
  [wait for response]
  Message 2: Read("file2.txt")
  [wait for response]
  Message 3: Read("file3.txt")

  Time: 9 seconds (3 round trips)

✅ Good:
  Single message:
    Read("file1.txt")
    Read("file2.txt")
    Read("file3.txt")

  Time: 3 seconds (1 round trip)

IMPACT
------
- 3x slower execution
- Wasted time
- Compounds across workflow

FIX
---
Before each message, ask:
"Are any of these operations independent?"
If yes: Batch them in single message

MEASURED COST (Real Example)
-----------------------------
KGF project without parallelization: ~6 hours
KGF project with parallelization: ~4 hours
Waste from anti-pattern: 2 hours (33% of project time)

-----------------------------------------------------------------------------
3.2 NO VALIDATION BETWEEN STAGES
-----------------------------------------------------------------------------

ANTI-PATTERN
------------
Generating multiple outputs without validation, then checking at end.

EXAMPLE
-------
❌ Bad:
  Stage 1: Generate data → Write("data1.json")
  Stage 2: Generate data → Write("data2.json")
  Stage 3: Generate data → Write("data3.json")
  [finally validate]
  Error in data1: Rework all three stages

✅ Good:
  Stage 1: Generate data → Write("data1.json")
         Bash: jq '.' data1.json → Validate immediately
  Stage 2: Generate data → Write("data2.json")
         Bash: jq '.' data2.json → Validate immediately
  Stage 3: Generate data → Write("data3.json")
         Bash: jq '.' data3.json → Validate immediately

IMPACT
------
- Errors compound
- Massive rework needed
- Lost time (10+ minutes per stage to fix)

FIX
---
Validate immediately after each significant operation:
  - After Write: Check syntax/format
  - After Edit: Run tests
  - After Bash: Check exit code and output

MEASURED COST
-------------
Without validation: 30 minutes rework when errors found
With validation: 2 minutes total validation time, errors caught early
Waste from anti-pattern: 28 minutes

-----------------------------------------------------------------------------
3.3 MONOLITHIC GENERATION FOR LARGE OUTPUTS
-----------------------------------------------------------------------------

ANTI-PATTERN
------------
Attempting to generate very large, complex output in single operation.

EXAMPLE
-------
❌ Bad:
  Generate all 30 nodes with relationships in one generation
  Problems:
    - Context overflow
    - Inconsistent formatting
    - Hard to debug
    - Can't resume on error

✅ Good:
  Generate 5 capabilities → Write("cap.json")
  Generate 5 patterns → Write("pat.json")
  Generate 7 skills → Write("skill.json")
  Generate 13 techniques → Write("tech.json")
  Combine: Bash: jq -s '{nodes: .[0].nodes + .[1].nodes + ...}'

IMPACT
------
- Lower quality output
- More errors
- Context overflow
- Complete loss if error occurs

FIX
---
For outputs >1000 lines or >5 distinct sections:
  1. Break into logical chunks
  2. Generate each chunk separately
  3. Write each to file
  4. Combine programmatically

THRESHOLD
---------
Use monolithic: Output <500 lines, single cohesive piece
Use progressive: Output >1000 lines, multiple sections

-----------------------------------------------------------------------------
3.4 NOT USING SPECULATIVE READS
-----------------------------------------------------------------------------

ANTI-PATTERN
------------
Sequential file discovery when parallel speculative reads would be faster.

EXAMPLE
-------
❌ Bad:
  Glob("**/*.py") → Get 10 files
  Read first file → Check relevance
  Not useful, try next
  Read second file → Check relevance
  Not useful, try next
  Read third file → Finally useful!

  Time: 3 round trips = 9 seconds

✅ Good:
  Glob("**/*.py") → Get 10 files
  Speculatively read 5 potentially useful files in parallel
  Evaluate all 5, use 3

  Time: 1 round trip = 3 seconds (even with 2 "wasted" reads)

IMPACT
------
- 3x slower discovery
- Many round trips
- Wasted time

FIX
---
When exploring codebase with unclear structure:
  1. Glob to identify candidates
  2. Read 5-10 candidates in parallel
  3. Evaluate which are useful
  4. Use what you need

Even 50% "waste" is faster than sequential discovery.

-----------------------------------------------------------------------------
3.5 USING BASH FOR FILE OPERATIONS
-----------------------------------------------------------------------------

ANTI-PATTERN
------------
Using Bash (cat, grep, find) when specialized tools exist.

EXAMPLE
-------
❌ Bad:
  Bash: cat file.txt
  Bash: grep -r "pattern" .
  Bash: find . -name "*.py"

✅ Good:
  Read("file.txt")
  Grep(pattern="pattern")
  Glob("**/*.py")

IMPACT
------
- Slower execution
- Less clear code
- Manual output parsing needed
- Misses optimization opportunities

FIX
---
Use specialized tools for file operations:
  - Finding files: Glob (not find)
  - Searching content: Grep (not grep via Bash)
  - Reading files: Read (not cat)
  - Writing files: Write (not echo >)
  - Editing files: Edit (not sed)

Use Bash only for:
  - System commands (git, npm, pytest)
  - Complex pipelines (jq, awk combinations)
  - Operations not covered by specialized tools

-----------------------------------------------------------------------------
3.6 BLOCKING ON LONG OPERATIONS
-----------------------------------------------------------------------------

ANTI-PATTERN
------------
Waiting for long operations to complete instead of using background mode.

EXAMPLE
-------
❌ Bad:
  Bash: pytest tests/ (takes 5 minutes)
  [blocked, can't do anything]
  Wait for completion
  Continue with other work

✅ Good:
  Bash(command="pytest tests/", run_in_background=True)
  [immediately available for other work]
  Work on documentation
  Work on other code
  Later: BashOutput(bash_id) to check results

IMPACT
------
- 5 minutes blocked (wasted)
- Can't multitask
- Serial execution when parallel possible

FIX
---
For operations >1 minute:
  1. Use run_in_background=True
  2. Continue with other work
  3. Check results with BashOutput when ready

THRESHOLD
---------
Use foreground: Operations <1 minute
Use background: Operations >1 minute

-----------------------------------------------------------------------------
3.7 KEEPING EVERYTHING IN CONTEXT
-----------------------------------------------------------------------------

ANTI-PATTERN
------------
Accumulating all intermediate results in context instead of using files.

EXAMPLE
-------
❌ Bad:
  Stage 1: Generate 5000-line result → Keep in context
  Stage 2: Generate 5000-line result → Add to context
  Stage 3: Generate 5000-line result → Add to context
  Context: 15000 lines, overflow imminent

✅ Good:
  Stage 1: Generate result → Write("stage1.json") → Keep summary: "Stage 1: 5 items"
  Stage 2: Read("stage1.json") → Process → Write("stage2.json") → Keep summary
  Stage 3: Read("stage2.json") → Process → Write("stage3.json") → Keep summary
  Context: ~150 tokens for summaries, fresh and manageable

IMPACT
------
- Context overflow
- Can't continue workflow
- Lose all progress

FIX
---
For multi-stage workflows:
  1. Write each stage output to file
  2. Keep only summary in context
  3. Read files as needed for next stage
  4. Context stays fresh throughout

-----------------------------------------------------------------------------
6.1 THE LATENCY DOMINANCE PRINCIPLE
-----------------------------------------------------------------------------

INSIGHT
-------
Round-trip latency dominates execution time, not individual operation cost.

EXPLANATION
-----------
Individual operation times:
  Read file: ~2 seconds
  Round trip: ~3 seconds per message

Impact:
  5 sequential reads: 5 messages = 15 seconds (latency dominates)
  5 parallel reads: 1 message = 3 seconds (latency minimized)

IMPLICATION
-----------
Optimize for fewer round trips, not fewer operations.
"Wasting" operations in parallel is faster than saving them sequentially.

EXAMPLE
-------
Speculative reading wastes 40% of reads but saves 60% of time:
  Read 5 files (2 unused) in parallel: 3 seconds
  Read 3 files sequentially: 9 seconds

40% waste, but 3x faster overall.

PRINCIPLE
---------
"Minimize round trips, not operations"

-----------------------------------------------------------------------------
6.2 THE PROGRESSIVE ASSEMBLY PRINCIPLE
-----------------------------------------------------------------------------

INSIGHT
-------
Complex outputs are better built through assembly than monolithic generation.

EXPLANATION
-----------
Monolithic generation of 10,000-line output:
  - Context strain
  - Inconsistency
  - Hard to debug
  - All-or-nothing

Progressive assembly (10 sections × 1000 lines):
  - Fresh context per section
  - Consistent formatting
  - Easy debugging
  - Recoverable

ANALOGY
-------
Like manufacturing:
  Don't build entire car in one mold
  Build components separately, assemble

PRINCIPLE
---------
"Divide, conquer, assemble"

-----------------------------------------------------------------------------
6.3 THE VALIDATION CHECKPOINT PRINCIPLE
-----------------------------------------------------------------------------

INSIGHT
-------
Early validation prevents compounding errors, saves time overall.

EXPLANATION
-----------
Cost of validation: 30 seconds per stage
Cost of rework: 10+ minutes per stage

Without validation:
  Error in stage 1 discovered in stage 5
  Rework: All 5 stages = 50+ minutes

With validation:
  Error in stage 1 caught immediately
  Fix: 30 seconds + 10 minutes = 10.5 minutes

ROI: 80% time saved

PRINCIPLE
---------
"Validate early, validate often"

-----------------------------------------------------------------------------
6.4 THE SPECIALIZATION EFFICIENCY PRINCIPLE
-----------------------------------------------------------------------------

INSIGHT
-------
Specialized tools outperform general-purpose tools for specific operations.

EXPLANATION
-----------
Bash can do everything, but:
  - Glob is faster for finding files
  - Grep is faster for searching content
  - Read is faster for loading files
  - Edit is cleaner for modifications

Why:
  - Optimized for specific operation
  - Structured output (no parsing)
  - Better error handling
  - Built-in parallelization

ANALOGY
-------
Swiss Army knife vs dedicated tools:
  Swiss Army knife: Can cut, saw, file
  Dedicated saw: Better at sawing

PRINCIPLE
---------
"Right tool for right job"

-----------------------------------------------------------------------------
6.5 THE CONTEXT PRESERVATION PRINCIPLE
-----------------------------------------------------------------------------

INSIGHT
-------
External storage preserves context better than internal memory.

EXPLANATION
-----------
Context memory is finite:
  - Fills up with results
  - Prevents long workflows
  - Loses work on overflow

File storage is unlimited:
  - Write results to files
  - Keep summaries in context
  - Read back as needed
  - Fresh context each stage

ANALOGY
-------
Like computer memory management:
  RAM: Fast but limited (context)
  Disk: Slower but unlimited (files)

Good systems use both appropriately.

PRINCIPLE
---------
"Store externally, summarize internally"

-----------------------------------------------------------------------------
6.6 THE COMPOUND OPTIMIZATION PRINCIPLE
-----------------------------------------------------------------------------

INSIGHT
-------
Small optimizations compound across workflow for major impact.

EXPLANATION
-----------
Single optimization (parallelization):
  5 operations: 15s → 3s (5x faster)

Applied systematically:
  10 groups of 5 operations: 150s → 30s (5x faster)
  But: Saves 2 minutes per group × 10 groups = 20 minutes saved

In 4-hour project:
  Many small optimizations
  Compound to 33% time savings (2 hours)

ANALOGY
-------
Like compound interest:
  1% daily improvement = 37x improvement annually
  3x speedup per operation × 20 operations = massive time savings

PRINCIPLE
---------
"Small gains compound to large wins"

-----------------------------------------------------------------------------
6.7 THE FAIL-FAST PRINCIPLE
-----------------------------------------------------------------------------

INSIGHT
-------
Finding errors early prevents wasted work on flawed foundation.

EXPLANATION
-----------
Late error detection:
  Build 5 stages on flawed foundation
  Discover error in stage 1 at stage 5
  Rework: All 5 stages

Early error detection:
  Validate stage 1 immediately
  Find error, fix immediately
  Continue on solid foundation

Cost:
  Late detection: 50+ minutes rework
  Early detection: 10 minutes fix
  Savings: 80%

PRINCIPLE
---------
"Fail fast, fix fast, proceed confidently"
